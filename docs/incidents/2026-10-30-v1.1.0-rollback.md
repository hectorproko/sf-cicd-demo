# Incident: v1.1.0 rollback (2026-10-30)

Personal learning project. Blameless format.

## Summary
v1.1.0 raised the expense approval threshold from $500 to $1000 and added the
Category_Required validation rule. Finance rejected the new threshold, so PROD was
restored to v1.0.0 behavior as release v1.1.1. Two earlier failures during the
v1.1.0 cycle are included because they shaped the fix.

## Impact
- PROD ran the $1000 threshold from run 20261030.5 until run 20261030.9.
- No data impact (PROD had 0 Expense__c records).

## Timeline
| Run / PR | Event |
|---|---|
| PR (threshold) | Validation failed: 3 tests still asserted the $500 rule. Fixed by deriving test amounts from APPROVAL_THRESHOLD and pinning the value in one test. |
| Manual change | Validation rule Category_Required added directly in QA (simulated drift). |
| QA deploy after merge | Failed: handlesBulkInsert hit FIELD_CUSTOM_VALIDATION_EXCEPTION. Deploy is atomic, so QA stayed on $500. |
| PR 4 | Rule retrieved from QA into source, bulk test sets Category. QA deploy succeeded. |
| 20261030.5 | v1.1.0 deployed to PROD after approval. Tagged v1.1.0. |
| Hotfix revert | Validation failed: the revert removed the rule from source, but deploys do not delete, so the rule stayed and the v1.0.0 bulk test failed. |
| PR 7 / 20261030.8 | Added destructiveChangesPre.xml and pipeline support for destructive manifests. Validated against PROD. |
| 20261030.9 | Rollback deployed to PROD after approval. Tagged v1.1.1 after gated verification. |
| PR 8 / 20261030.11 | main back-merged into develop. QA rolled back. Parity check passed. |
| PR 9 | Release-scoped destructive manifest removed from develop. |

## Root causes
1. Tests hardcoded business values instead of reading the rule.
2. A manual change in QA bypassed source control (drift).
3. Salesforce deployments are additive. Rolling back added metadata needs explicit destructive changes.

## Process mistakes I made
- Tagged v1.1.0 before the PROD deploy finished, and once with a placeholder run number.
- Identified "the deploy run" as the latest run on main, which picked up an older run.
- Opened the hotfix PR into develop instead of main, so it validated against QA.

## What went well
- PR validation and atomic deploys meant no environment was ever half-updated.
- The PROD approval gate and environment history gave a clear audit trail.
- Every failure was caught by validation or verification before it caused harm.

## Changes made
- Tests derive amounts from the threshold constant.
- Pipeline supports pre-destructive manifests and prints them in the log.
- Runs are identified by commit (sourceVersion), not by recency.
- Tagging is gated on verified PROD state.

## Follow-ups
- Release the destructive-manifest removal to main.
- Restrict admin access in QA and PROD to stop drift; add scheduled drift detection.
- Add a post-deploy verification stage to the pipeline.
- Add path filters so documentation-only changes skip Salesforce validation.
